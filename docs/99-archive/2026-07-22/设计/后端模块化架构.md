# 智学伴后端 - 模块化架构设计

> 本文记录后端从「按技术层分层」演进为「按业务功能模块化」的目标架构形态，**对照当前真实文件**写。过程（为什么拆、分几阶段、怎么验证）见 `docs/requirements/13-后端按业务功能模块化拆分.md`，本文只讲形态与边界。

## 上位约束（依据）

本架构遵循两份仓库外约束（按编号引用，沿用 `app/core/ai_service.py` 注释既有写法，不复制条款、不两处维护）：

- **《通用架构编码约束》** `~/Documents/40-学习笔记/参考资料与规范/通用架构编码约束.md`（21 条，分两档）
- **《架构总论-内聚与耦合》** `~/Documents/40-学习笔记/参考资料与规范/学习笔记/架构.md`

本次迁移主要落在以下条款；其余项目已落实（如 **#18** LLM 超时/重试/熔断，见 `app/core/ai_service.py`、`app/utils/cos.py`）或按需套用：

| 编号 | 原则 | 本次如何体现 |
|---|---|---|
| #1 | 依赖单向向下，底层不感知上层 | feature → core 单向；feature 间禁止反向 import |
| #2 | 只依赖更稳定组件 | `agent_loop` 留 `core/`，被各 feature 复用，自身少变 |
| #6 | 先增内聚再解耦（因果不对称） | god module 先内部拆子模块再搬目录（见需求 §13） |
| #11 | 从最简方案起步 | 选模块化单体，不引入微服务/MQ/分布式缓存 |

第二档（#12~#21）按「服务化前提」套用：StudyBuddy 调 LLM/COS/微信等外部服务 → #18 适用且已落实；纯 CRUD 不上 DIP/防腐层（#12/#13 自标 ⚠️ 过度设计）。

## 1. 现状：按技术层分

```
app/
├── routers/     20 个文件，按 HTTP 入口平铺
├── services/    28 个文件，按业务逻辑平铺

│   ├── question_bank/
│   ├── exams/

│   ├── growth/
│   ├── learning/

│   └── wechat/

│   ├── auth/                  # auth_service、access_service

│   └── middleware/

├── utils/                     # 通用工具（复用现有，不新建 shared）
└── main.py
```

## 3. 三个区域的边界

| 区域 | 放什么 | 不放什么 |
|---|---|---|
| `features/<功能>/` | 这个功能的 router.py / service.py / schemas.py | ❌ ORM 模型（留 `models/`）<br>❌ 跨功能的通用件<br>❌ 别的 feature 的内部实现 |
| `models/` | 所有 ORM 表模型，集中管理 | ❌ 业务逻辑<br>（理由：项目用 `sql/001-020_*.sql` 增量脚本 + `scripts/run_ddl.py` 执行器维护表结构，`ensure_*.py` 为补充；表 ↔ model ↔ SQL 脚本靠编号人工对应，集中好对上） |
| `core/` | 跨所有功能的基础设施与编排：`agent_loop`、`ai_service`、数据库、鉴权、配置、通知 | ❌ 某个具体功能的业务（功能进 `features/`） |

### 4.3 重点模块子结构

两个模块在迁入 feature 时按子域拆子包，避免单文件再次膨胀：

**`features/growth/`**（7 个 service、最大块，必须拆子包）：

```
features/growth/
├── records/          # 事实层：daily_learning_record、daily_checkin、daily_summary
│   ├── service.py
│   └── router.py
├── summary/          # 派生层：growth_summary（家长摘要/AI 分析）、growth_intent
│   ├── service.py
│   └── prompts.py
├── supervision/      # 家长视角：supervision
│   ├── service.py
│   └── router.py
└── intent/           # 学生意图分类：growth_intent 若不放 summary 则单列
```

理由：`summary_service` 会继续长（家长周报、AI 分析），`records` 是事实层、`summary` 是派生层、`supervision` 是家长视角，三个不同子域，混在一个 service.py 会再造 god module。迁移时顺手消高1/中4/中5。

**`features/materials/`**（预留 providers/，AGENTS.md 已提要接 Docling/marker/MinerU）：

```
features/materials/
├── providers/         # 外部解析器适配层（未来接入）
│   ├── docling_provider.py
│   ├── mineru_provider.py
│   └── marker_provider.py
├── extraction_service.py   # 现 markdown_extraction_service
├── ocr_service.py          # 现 markdown_ocr_service（CLI OCR 薄封装）
└── service.py              # 门面
```

理由：素材识别 provider 以后会换/加，隔离成 providers/ 层，切换不污染主 service。迁移时顺手消中3（视觉编码重复）。

## 5. 跨功能依赖图（真实，DAG 无环）

```
core/agent/agent_loop ──调用──> 所有 features/*/service（编排层，唯一跨全域）

features/question_bank ──> features/materials（用 markdown_extraction 视觉）
features/exams ──> features/error_book（exam_batch/grading/photo_grading 落错题）
features/learning ──> features/error_book（diagnosis 读错题）
features/learning ──> features/learning 内部（learning_flow -> diagnosis）
features/growth ──> features/growth 内部（summary -> daily_record）
features/growth ──> features/profile（读 study_plan 完成事实）

features/error_book    无下游（底层，被 exams + learning 依赖）
features/materials     被 question_bank 跨域依赖（视觉能力共享）
```

依赖方向单向，现状已是 DAG，迁移时保持。feature 之间只调对方 `service.py` 的公开函数，不直接写对方 model 的 SQL。

## 6. main.py 挂载方式

挂载逻辑不变，只换 import 路径：

```python
from app.features.question_bank.router import router as question_bank_router
from app.features.exams.router import router as exam_router
from app.features.exams.router_exam_batch import router as exam_batch_router
# ...
app.include_router(question_bank_router)
app.include_router(exam_router)
```

`APIRouter(prefix="...")` 那行**逐字不改**（见 §4.1 的 prefix 列），前端 `src/api` 零感知。

## 7. 边界与依赖规则

1. **API prefix 逐字不变**：§4.1 列出的 20 个 prefix 是硬约束，迁移只挪文件 + 改 import，不动 prefix / 路由函数 / response_model。
2. **依赖单向**：`router -> service -> model`；feature 之间走对方 service 公开函数，不反向、不循环。
3. **`agent_loop` 是唯一跨全域编排层**，留 `core/agent/`，可调所有 feature 的 service；但它不放进任何单一 feature。
4. **ORM 留 `models/`**：feature 不放表模型，兼容手写 SQL 建表脚本的人工对应。
5. **过渡双轨**：`routers/`、`services/` 不一次性清空，迁完一个 feature 清一个，未迁的保持原位工作。

### 9.1 前端拆分原则

1. **API 跟着功能走，不留 `src/api/` 大目录**：`features/error_book/api.ts` 而非 `api/errorBook.ts`。改错题只进 `features/error_book/` 一个目录（page + api + types + hooks 全在），不再跳 pages/api/types 三处。
2. **types 拆分，不留 941 行 `index.ts`**：`ErrorBookItem` 进 `features/error_book/types.ts`，`MaterialItem` 进 `features/materials/types.ts`。全局 `src/types/` 只留 `api.ts`（ApiResponse/Pagination）、`auth.ts`（User/Token）、`common.ts`（ID/Timestamp）。原则：谁拥有数据结构谁维护。
3. **`shared/` 只放真跨域的**：UI 基础件（Button/Input/EmptyState/LoadingOverlay/PageHeader/AppPageShell）、布局、通用 hooks（useAuth/usePolling）、HTTP 基础设施（http.ts/authInterceptor）。**不放业务组件**（ErrorBookCard/LearningMapNode/ExamQuestionCard 进各自 feature 的 components/）。
4. **chat 保守**：`features/chat/`（ChatPage + chatStore + MessageBubble + TodayPlanPanel），不提前抽 shared。等真出现「首页/错题页内嵌聊天」再把 chatStore 抽到 `shared/stores/`。
5. **today 单独成 feature**：产品核心，承载今日计划/今日总结/继续学习。前端聚合，后端跨 `features/growth/`（daily_checkin/daily_record）+ `features/learning/`（learning_flow）。
6. **路由按 feature 注册**：各 feature 导出 `routes`，`app/router.tsx` 聚合。当前是 `react-router-dom` 的 `HashRouter + <Routes>` 集中在 `App.tsx`，迁移时拆成各 feature routes 数组聚合，新增功能不改巨大 router 文件。
7. **API 路径不变**：前端拆的是代码组织，HTTP 调用路径和后端 prefix 一样逐字不变。
