# 错题优先上下文 MVP Design

## 背景

知了的差异化不是“更强 AI 答题”，而是 **学生自己的学习数据 + 家庭督促场景 + 长期记忆教练**。当前系统已经有错题本、错因反馈、错题复盘笔记、每日回顾和学习计划，但 Agent 还没有稳定形成“先看这个学生最近反复错什么，再给建议”的工作方式。

这会导致两个问题：

- 学生问“今天英语怎么学”“给我练一练”时，Agent 可能生成通用计划，而不是基于近期错题和笔记。
- 错题复盘笔记已经能沉淀，但后续对话没有稳定把这些笔记拿回来用，价值容易断掉。

本 MVP 要补的是 Agent 的上下文编排，不是新建一套记忆系统。

## 目标

- Agent 在讲题、制定计划、复盘、推荐练习前，优先读取学生近期错题、错因、错题复盘笔记和高频知识点。
- 回答时尽量说明依据，例如“我看到你最近在一般过去时错了 3 次”或“你之前的复盘笔记里写到单位换算容易漏”。
- 没有足够错题/笔记数据时，不编造历史，明确说“目前错题数据还少”，再给轻量建议或引导上传/记录错题。
- 学习计划仍保持“先商量再创建”：错题上下文只能用于生成草案和追问，不能绕过学生确认。
- 先复用现有 MySQL 数据和 service，不引入 mem0、向量库、图数据库或新 UI。

## 非目标

- 不做新的学习地图页面。
- 不新增长期记忆数据库。
- 不自动把所有错题生成笔记。
- 不让 Agent 自动保存计划、笔记或错题掌握状态。
- 不做题库/试卷资源推荐的完整策略。
- 不改登录角色；学生/家长身份边界沿用现有逻辑。

## 推荐方案

采用“后端自动注入简短学习记忆上下文”的方式。

对比方案：

| 方案 | 做法 | 优点 | 问题 |
|---|---|---|---|
| A. 只强化工具调用提示词 | 要求 Agent 自己先调用 `query_error_book`、`query_notes`、`query_feedback` | 改动小 | 不稳定，用户说法模糊时容易忘查 |
| B. 自动注入学习记忆上下文 | 后端在相关对话前拼一段压缩上下文给模型 | 稳定、少改 UI、复用现有数据 | 需要控制长度和触发场景 |
| C. 接 mem0/向量库 | 把错题、笔记、素材都写入外部记忆 | 长期可扩展 | 当前过重，会拖慢 MVP |

本次选择 B。C 作为后续素材 Markdown 化、学习地图、长期检索量上来后的评估方向。

## 数据来源

第一版只读已有数据：

| 数据 | 来源 | 用途 |
|---|---|---|
| 高频知识点/盲区 | `note_service.get_blind_spots(db, student_id, min_errors=2)` | 知道反复错的知识点和是否已有笔记 |
| 代表性错题 | `diagnosis_service.get_error_book(db, student_id)` | 给 Agent 看到题干、学生答案、正确答案、错题次数 |
| 错题复盘笔记 | `note_service.list_notes(db, student_id)`，筛选 `category=错题复盘` 或 `source=错题讲解` | 引用学生确认过的错因、方法、下次提醒 |
| 近期错因反馈 | 现有 `_build_profile_context` 已读取 `p2_service.list_feedback` | 判断粗心、概念不清、审题等错因趋势 |
| 每日回顾 | 现有 `_build_profile_context` 已读取最近每日回顾 | 结合昨天状态和今天目标 |

素材 Markdown 化完成后，再把 `confirmed_markdown` 和素材摘要纳入本上下文；本 MVP 不等待素材链路。

## 触发场景

第一版建议保守触发，避免每次闲聊都塞上下文。

需要注入“错题优先上下文”的场景：

- 讲题、批改、解释错题、问“我哪里错了”。
- 制定学习计划、问“今天/下午/周末怎么学”。
- 推荐练习、生成同类题、问“练一下”。
- 复盘、总结、问“最近哪里薄弱”。
- 家长问“最近要督促什么”“哪里反复错”。

不强制注入的场景：

- 纯登录、帮助、页面操作问题。
- 普通寒暄。
- 上传素材刚开始且尚未识别完成。
- 明确和学习无关的生活闲聊。

实现上可以先用轻量关键词判断；如果拿不准，宁可注入一段很短的摘要，而不是完全没有学习记忆。关键词应集中在 helper 中，不能散落硬编码。

## 上下文内容格式

新增一个独立 builder，例如 `_build_learning_memory_context(db, student_id, latest_user_text)`，不要继续把所有东西塞进 `_build_profile_context`。

输出示例：

```text
[学习记忆]
近期高频错题：一般过去时错 3 次，最近 2026-07-05，已有 1 篇笔记；分数应用题错 2 次，暂无笔记。
代表性错题：
1. error_id=12，知识点=一般过去时，题干=题干摘要，学生答案=学生作答摘要，正确答案=正确答案摘要，错过 2 次。
2. error_id=18，知识点=分数应用题，题干=题干摘要，学生答案=学生作答摘要，正确答案=正确答案摘要，错过 1 次。
错题复盘笔记：
1. 《一般过去时复盘》：下次先找时间标志词，再判断动词过去式。
使用要求：计划、讲题、推荐练习前先参考这些数据；引用时说清依据；没有数据时不要编造。
```

长度控制：

- 高频知识点最多 5 个。
- 代表性错题最多 5 道。
- 错题复盘笔记最多 3 篇。
- 单个题干/答案/笔记摘要限制 80-120 字。
- 整段上下文目标控制在 1200 中文字以内。

## Agent 行为规则

- 讲题时：先批改，再给正确答案、错误点、知识点和下次提醒；如果上下文里有相关历史错题，要指出“这类点之前也错过”。
- 制定计划时：先说明依据，再问学生可用时长、目标和是否按草案执行；确认前不调用 `create_study_plan`。
- 推荐练习时：优先围绕高频错题和未沉淀笔记的知识点；不要为了显得强而生成太多题。
- 复盘时：优先把错题、错因、笔记、每日回顾串起来，指出一两个最值得补的点。
- 保存笔记时：仍必须让学生确认，不能把自动上下文当成学生确认。
- 数据缺失时：明确说数据少，并引导学生上传错题、记录错因或写每日回顾。

## 架构设计

### 后端

在 `agent_loop.py` 增加独立学习记忆上下文构建：

- `_should_include_learning_memory(latest_user_text: str) -> bool`
- `_build_learning_memory_context(db: Session, student_id: int, latest_user_text: str) -> str`
- `_summarize_error_book_groups(groups: list[Any]) -> list[str]`
- `_summarize_error_review_notes(notes: list[Any]) -> list[str]`

调用位置放在现有 profile context 之后、模型请求之前。这样系统上下文顺序为：

1. 基础 system prompt。
2. 学生画像上下文。
3. 学习记忆上下文。
4. 历史消息。

读取失败时只记录 warning，不阻塞对话。

### 前端

本 MVP 不改前端 UI。后续如果要让学生看见“AI 本次参考了什么”，再考虑工具卡片或引用来源卡。

### 文档

实现后更新：

- `docs/已实现能力清单.md`
- `docs/未实现需求清单.md`
- `studybuddy-client/src/data/releaseNotes.ts`
- 必要时更新 `docs/真人验收指南.md`

## 权限与边界

- student 只能读取自己的学习记忆。
- teacher/家长只能读取已绑定学生的数据，沿用现有 `_resolve_tool_student_id` / access service 边界。
- 自动注入的上下文只给模型使用，不直接暴露完整隐私明细到页面。
- 如果后续展示引用来源，必须只展示当前用户有权限看的错题/笔记。

## 错误处理

- 错题服务异常：跳过错题上下文，保留画像和正常对话。
- 笔记服务异常：跳过复盘笔记摘要。
- 数据为空：返回空串或“数据较少”的短提示，不制造假上下文。
- 上下文过长：按高频知识点、最近错题、最近复盘笔记顺序截断。

## 验收标准

### 自动化验收

- 单测：粗略学习计划请求命中 `_should_include_learning_memory`。
- 单测：普通帮助/登录问题不命中或只返回空学习记忆。
- 单测：有高频错题和复盘笔记时，builder 输出包含知识点、错题次数、代表性错题、笔记摘要。
- 单测：builder 输出长度受控，长题干/长笔记会截断。
- 单测：服务异常不影响 Agent 主流程。
- Agent 行为测试：用户只说“今天英语怎么学”，模型上下文包含学习记忆，但没有确认时不能落库创建计划。

### 浏览器/真人验收

使用学生账号登录后：

1. 准备至少一条英语或数学错题，带错因反馈和一篇错题复盘笔记。
2. 在聊天页问：“今天英语怎么学？”
3. 期望 AI 先提到近期错题/错因/笔记依据，再给计划草案并询问是否可行。
4. 直接刷新或切换页面回来，继续问：“给我练两道类似的。”
5. 期望 AI 仍围绕同一薄弱知识点，而不是随机出题。
6. 说“可以，创建计划”后才允许落库创建学习计划。

验收重点不是 AI 话术多华丽，而是它是否真的基于学生自己的数据。

## 后续实现计划入口

实现计划应拆成小步：

1. 新增学习记忆上下文 builder 和触发判断。
2. 给 builder 加单测，覆盖数据为空、数据存在、长度截断、异常兜底。
3. 接入 Agent 主循环。
4. 加 Agent 行为测试，确认计划仍需用户确认。
5. 本地跑后端测试和前端无改动检查。
6. Codex 浏览器用学生账号验收聊天行为。
7. 更新帮助与更新、已实现/未实现文档。
8. 如用户确认，再走部署脚本上线。
