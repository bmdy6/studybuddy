# 微信学习助手对话式学习入口

## 定位

学生普通文本已纳入当前 MVP：复用现有 Agent 和固定微信 ChatSession，只发送最终结果。本文后续只跟踪图片、语音、文件、结构化进度事件和可恢复长任务。

它仍然不是 Web 快速登录入口，不在微信里复制完整网页。学生账号仍不通过微信自动注册；家长可按 `09-微信学习助手推送MVP.md` 的学生邀请流程自动创建不可网页登录的渠道身份。

## 用户问题

微信没有 Web 页面的加载卡片和实时工具状态。学生发送一张试卷后，如果十几秒没有回复，会以为图片没有收到或系统卡住。如果直接显示“调用 OCR”“调用工具”“查询数据库”，又会把内部实现暴露给学生和家长，不能解释真正进度。

需要让用户始终知道：

1. 消息或图片已经收到。
2. 系统正在做什么用户能理解的事。
3. 处理完成后会返回什么，是否还需要用户确认。
4. 处理失败时如何重试或回到 Web 完成。

## 与当前微信 Bot MVP 的区别

| 维度 | 当前 MVP | 后续对话式入口 |
|---|---|---|
| 核心目标 | 绑定、文本学习对话、学情查询和定时提醒 | 增加微信媒体和可恢复长任务 |
| 输入 | 绑定码、学生普通文本、家长学情提问和首次数字配置 | 错题/试卷图片；语音、文件后续评估 |
| 处理 | 后端确定性 service + 共享 Agent loop | 继续复用现有 Agent 和业务工具 |
| 回复 | 文本对话有最终结果或失败说明 | 图片和长任务增加必要的阶段状态和任务恢复 |
| 图片 | 不转发业务后端 | 进入现有素材或错题候选链路 |
| 用户确认 | 命令当场生效 | 识别稿、错因、薄弱点、笔记和试卷仍遵守现有确认边界 |
| 登录 | 不作为 iLink Bot 主能力 | 仍不通过 Bot 实现快速登录 |
| 复杂交互 | 不支持 | 继续跳 Web 完成长试卷作答、逐题修正和复杂编辑 |

## 交互流程

### 短文本任务

```text
学生发送支持的学习问题
-> 后端根据已绑定账号进入同一学生上下文
-> 识别为当前开放的学习意图；未开放的操作说明限制并引导到 Web
-> 快速任务直接返回结果
-> 处理较慢时先回“已收到，正在查找相关学习记录”
-> 完成后返回简短答案和必要的 Web 链接
```

### 试卷或错题图片

```text
学生发送图片
-> 立即回“已收到这张图片，正在识别题目和作答”
-> 复用现有图片识别和错题候选流程
-> 必要时发一条阶段状态
-> 返回识别摘要、不确定项和下一步
-> 需要逐题修正或确认时跳转 Web
```

识别结果默认是候选稿。没有学生确认时，不自动把识别错误写入错题本、长期记忆、正式笔记或薄弱点。

## 状态反馈

微信不展示内部工具名、模型名、数据库查询或思考过程。后端把现有 `tool_progress` 事件转换为用户能理解的任务状态：

| 内部任务 | 微信可见文案示例 |
|---|---|
| 读取试卷或错题图片 | 正在识别试卷内容 |
| 核对题目和作答 | 正在整理题目和作答 |
| 分析错题 | 正在分析错题和知识点 |
| 读取学习记录 | 正在查找相关学习记录 |
| 生成针对练习 | 正在根据错题和素材准备练习 |
| 搜索讲解资源 | 正在查找适合的讲解 |

反馈原则：

- 收到图片和明显慢任务时先发一条回执，快速文本问答不额外发“正在处理”。
- 只在状态真正变化且用户仍在等待时发进度，不按固定秒数刷屏。
- 同一任务最多保留少量关键阶段，不把每个工具调用都发给用户。
- 最终结果到达后不再发旧进度；重试和超时不得造成结果乱序。
- 处理失败必须给出用户能执行的下一步，不回传内部堆栈和 provider 错误。
- 状态节流、任务超时和最大消息数由部署配置或集中策略控制，不在业务分支里散落硬编码。

## 架构边界

```text
iLink Bot / WeixinAdapter
  -> 验证已绑定微信身份
  -> 统一为渠道文本或媒体输入
  -> 智学伴后端为唯一业务和权限边界
  -> 复用现有 Agent loop 与 service
  -> 渠道投递器发送回执、进度和最终结果
```

- Bot 微服务仍不访问 MySQL，不理解错题、笔记或试卷业务。
- 后端按内部用户 ID 读取权限、学习资产和记忆；`provider_account_id + ilink_user_id` 只用于渠道身份和投递。
- Web 和微信复用同一套业务 service，不为微信重写素材、错题、笔记、试卷或记忆逻辑。
- 当前 Web SSE 已有 `tool_progress` 事件，后续需要增加渠道状态映射和可恢复投递，不能直接把 SSE 字段原样发到微信。
- 文字、图片和长任务都必须有消息幂等键，避免 iLink 重投、超时重试或进程重启造成重复落库和重复回复。

长任务的队列、恢复和投递形式在实施 spec 中再根据项目现有能力选型；本需求不预先引入新 MQ 或通用渠道平台。

## 权限与确认

- 学生只服务已绑定的现有智学伴账号；渠道家长只能由已登录学生的有效邀请创建。
- 学生只能读写自己的学习数据；家长只能访问 `teacher_students` 内已有关系。
- 普通识别结果和 AI 推断默认为候选，不直接写正式学习事实。
- 创建计划、保存笔记、落错题、修改画像和生成正式试卷继续复用现有确认流程。
- 微信不展示模型 reasoning、内部 prompt、工具参数、调试日志或原始 provider 错误。

## 分期

### 阶段 0：当前微信 Bot MVP

- 修复同一用户连续命令的回复稳定性。
- 完成绑定、家长学情查询、提醒设置、定时推送、解绑和双微信隔离验收。
- iLink Bot 不承担快速登录。

### 阶段 1：文本学习对话（已实现）

- 已绑定学生的普通文本进入现有 Agent，不复制 Agent、Prompt、工具和学习记忆。
- 同一微信消息串行处理，不同微信可以并发。
- 每条普通文本只主动发送最终结果或失败说明，不额外发送固定处理中回执。

### 阶段 2：图片和长任务反馈

- 微信图片进入素材或错题候选链路。
- 接入回执、阶段状态、最终结果和失败兜底。
- 用真实试卷验证识别准确性、等待时间、乱序和重复投递。

### 阶段 3：主动学习建议

- 基于已确认错题、薄弱点和计划结果，询问是否生成针对练习或试卷。
- 仍然由用户确认后才生成或保存，不自动堆积学习任务。

## 验收标准

- 已绑定学生在微信发文字后，使用与 Web 相同的内部用户、权限和学习记忆，不串号。
- 发送试卷或错题图片后快速收到用户语言回执，不显示 OCR、工具名和数据库等技术词。
- 长任务最终必须到达成功结果或失败说明，不停在“正在处理”。
- 快速任务不因状态回复变得啦嗦；慢任务不因无回馈让用户误以为卡死。
- 图片重投、网络重试和进程重启不会重复落错题、笔记或试卷。
- 未绑定、已解绑或无权限用户不能访问学习数据。
- 两个微信用户的图片、任务状态、最终结果和 context token 完全隔离。

## 本期不做

- 不改变当前微信 Bot MVP 的业务范围。
- 不为微信重写一套 Agent 或学习业务。
- 不把所有自然语言无条件送入 Agent，也不把微信做成无限制聊天入口。
- 不通过 iLink Bot 快速登录或自动注册学生；渠道家长身份和亲子关系只按已确认的学生邀请流程创建。
- 不在微信里做长试卷作答、逐题表格编辑、题库审核和后台管理。
- 不在这个需求阶段引入新 MQ、通用渠道平台或运营配置中心。
- 不在用户未确认时自动保存 AI 推断的错因、薄弱点、笔记或长期记忆。
