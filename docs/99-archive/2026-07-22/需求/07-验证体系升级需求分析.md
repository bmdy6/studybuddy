# 知了 — 验证体系升级需求分析

> **兼容说明（2026-07-17）**：本文的确认不变量继续保护计划、错题、笔记、画像和人工确认稿。根据 `12-每日教练与自动学习记录.md` 的明确授权，高置信非空素材识别结果可以作为 `machine_extracted` 自动保存和使用，但不能升级为 `verified`；测试必须验证来源、置信度、不确定点和人工确认稿优先级。每日摘要可以客观包含未完成数量，但这属于日报事实表达，不代表新增独立催办、异常提醒或自动改变计划。

## 背景

知了已经进入 P2 Agent 化阶段，风险不再只是页面能不能点、接口能不能通，而是：

1. **Agent 行为风险**：模型可能选错工具、编造参数、跳过确认。
2. **长期事实风险**：错题、笔记、素材确认稿、学习计划、画像会影响后续建议，一旦错误入库会持续污染。
3. **多步骤状态风险**：拍题识别、逐题确认、计划草案、试卷分发、任务完成/跳过都存在状态流。

当前已有 pytest、Vitest、live 测试、浏览器验收和上线复验，能挡住常规回归。但对“任意输入”“非法状态”“状态空间”的保护还不够系统。

## 目标

- 给关键流程补一层“业务不变量”保护。
- 优先引入轻量、贴合当前技术栈的验证方法。
- 不为了形式化验证牺牲 P2 功能交付速度。
- 让后续需求/spec 默认写清楚状态集合、状态迁移和不可违反的规则。

## 非目标

- 不迁移 Rust、Haskell、Lean 或 Coq。
- 不要求所有业务逻辑做形式化证明。
- 不用 TLA+ 替代 pytest、live 测试和浏览器验收。
- 不新增第二套业务状态机框架。
- 不为了验证而重写现有 service。

## 需要保护的边界

| 边界 | 主要风险 | 建议补强 |
|---|---|---|
| 学习计划草案确认 | 粗略目标直接落库、旧草案被确认 | 不变量清单 + 属性测试 + 状态流测试 |
| 素材 Markdown 来源分级 | 机器识别稿被伪装成人工确认事实或升级为 verified | 服务层系统测试 + 权限测试 |
| 拍题逐题核对 | 看不清却乱猜、确认答案错用 | human_reviewed 样本 + 确认状态不变量 |
| 学习地图 | 未确认素材影响掌握状态 | 属性测试保护状态规则 |
| 试卷分发权限 | 未分发学生看到试卷或提交 | 确定性系统测试 |
| Agent 工具调用 | 模型编造参数或绕过确认 | 工具 guard 测试 + live smoke |

## 推荐路线

### P0：业务不变量清单

每个高风险需求/spec 增加“业务不变量”小节。第一批不变量：

- 无有效计划草案确认，不能创建学习计划。
- 机器素材只能以 `machine_extracted` 使用，不能升级为 `verified` 或覆盖人工确认稿。
- 空白确认稿不能保存。
- 跨学生数据不能读取、提交或分发。
- 计划项全部完成/跳过后，计划不能继续保持 `active`。
- AI 生成草稿不能自动覆盖用户确认过的事实。

### P1：后端属性测试

引入 Python `hypothesis`，只测纯 service 或可控 service，不直接打真实 LLM。

首批对象：

1. `study_plan_confirmation_service`
2. `learning_map_service`
3. 素材确认/读取相关 service

验收标准：

- 进入默认后端非 live 测试。
- 不依赖网络、不消耗 token。
- 失败样例能缩小到可读输入。
- 每个测试只验证稳定不变量，不写成随机版业务流程测试。

### P1：服务层确定性系统测试

用固定时间、固定用户、固定 fixture、mock 外部返回来覆盖完整状态流。

首批流程：

1. 学习计划：创建、完成、跳过、逾期提醒、自动归档。
2. 素材 Markdown：上传、识别失败、重试、确认稿、Agent 读取确认稿。
3. 试卷分发：家长分发给 A，B 不可见，A 提交后状态变化。

验收标准：

- 一条测试能看清完整状态变化。
- 失败时能定位到具体步骤。
- 和 live 测试分工明确：系统测试保状态，live 测试保真实模型效果和耗时。

### P2：类型和状态收敛

持续减少裸字符串和多 boolean 状态：

- 后端状态字段优先用 `Literal`、枚举或集中常量。
- service 入参先 `strip()` 再判断空白。
- Agent 工具参数必须有 Pydantic/TypeScript 契约。
- 前端复杂异步状态使用显式状态字段，不用多个 boolean 互相猜。

### P3：TLA+ 试点

只在同一状态流反复出 bug 时试点，不进入日常门禁。

候选：

- 学习计划草案确认。
- 素材确认稿生命周期。
- 试卷分发权限。

进入条件：

- 同一流程出现 2 次以上状态类 bug。
- 普通单测/属性测试难以表达状态空间。
- 流程已经稳定，值得抽象成模型。

## 暂不排期

- Lean / Coq：当前投入产出不合适，只作为长期认知储备。
- 前端 `fast-check`：除非前端出现复杂纯逻辑状态机，否则暂不引入。
- 大规模 LLM 随机测试：token 成本高且结果不稳定，仍用 live smoke 和固定样本评测。

## 第一批实施建议

1. 给学习计划、素材确认、学习地图补业务不变量清单。
2. 新增 `hypothesis`，先给 `study_plan_confirmation_service` 写 2-3 条属性测试。
3. 补一条素材来源分级的服务层系统测试：机器稿保留 `machine_extracted`，确认后 Agent/读取端优先人工确认稿。
4. 把“业务不变量”写入项目新功能 spec 模板或 AGENTS 流程。

## 成功标准

- 新需求文档能明确说明业务不变量。
- 至少一个核心 service 有属性测试保护。
- 至少一条多步骤流程有确定性系统测试。
- 新增验证不依赖线上服务、不拖慢日常开发。
- 不引入重型形式化工具作为默认流程。
