# 知了代码审查流程

## 使用场景

用于审查知了当前 diff、指定 commit、分支、PR、发布候选或文档变更。默认只输出审查报告和建议；除非用户明确要求修复，否则不要直接改代码。

## 必读材料

审查前先读：

1. `AGENTS.md`
2. `docs/代码规范.md`
3. `docs/架构规范.md`
4. `docs/skills/zhixueban-release-verification/SKILL.md`
5. 与本次 diff 直接相关的需求、spec、测试和源码

## 审查流程

1. 确认审查范围：当前工作区、指定 commit、分支差异、PR diff 或指定文件。
2. 先建立本轮风险地图，再看具体代码：
   - 改动会影响哪些学生/家长可见行为。
   - 是否改变权限、数据归属、长期记忆、计划落库、素材确认、错题沉淀或部署流程。
   - 是否有重复造轮子、硬编码、隐藏兜底、吞异常、测试数据污染。
   - 哪些风险必须用浏览器、live、真实上传或公网 URL 才能验证。
3. 按严重程度输出 findings first。
4. 如果没有发现问题，也要说明检查范围、已验证证据、剩余风险和测试缺口。

## 知了重点检查项

- **产品体验**：是否从学生/家长视角合理；是否出现 AI 自嗨总结、自动保存、自动执行。
- **Agent 行为**：工具参数是否可信校验；计划是否先商量后确认；素材/笔记/错题是否保留用户确认。
- **权限与数据**：学生只能访问自己数据；家长只能访问绑定学生；测试数据不能混入正式用户。
- **架构边界**：router 不写业务细节；HTTP API、脚本、Agent 工具复用同一 service；可复用逻辑不要复制。
- **前端样式**：颜色、间距、卡片、状态标签是否沿用 token；是否有移动端溢出、按钮挤压、页面割裂。
- **测试验证**：TDD 是否覆盖原始问题；AI/视觉是否有 live 或真实 smoke 口径；浏览器验收是否从真实入口跑到成功状态。
- **文档上线**：帮助与更新、开发进度、已实现/未实现、踩坑清单是否同步；push 是否与真正上线区分。

## 输出格式

按下面顺序输出：

1. `发现的问题`：按 P0/P1/P2 排序。每条包含位置、证据、影响、建议修法、建议验证。
2. `开放问题或假设`：只列会影响判断的问题。
3. `验证情况`：列出已经看到的测试、构建、浏览器或部署证据；没有证据就写未验证。
4. `变更摘要`：简短说明本次 diff 在做什么。

文件位置优先用可点击路径；能定位行号时给行号。不要把猜测写成事实。

## 自检

输出前检查：

- 是否 findings first，而不是先夸总结。
- 是否每个问题都有证据和影响。
- 是否没有把通用清单机械套用到无关 diff。
- 是否明确未验证边界，尤其是浏览器、live、上线和真实数据。
- 是否没有直接修代码，除非用户明确要求。
